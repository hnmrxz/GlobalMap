# 07 · 架构决策记录（ADR）

> 每条 ADR 记录 **背景 → 决策 → 后果 → 被否决的选项**。决策的"为什么"比"是什么"更重要，尤其是在后来的维护者想改回去的时候。

## ADR-001: 数据源采用"三层零 Key + 显式降级链"，不把账号型 API 作为主路径

**状态**：已接受（2026-11-06）

### 背景
需求要求"尽量零 API Key"，同时要"最新影像 + 10 m 清晰度"。业内的标准答案（Copernicus Data Space 的 Sentinel Hub WMS）恰好需要免费账号 + OAuth 凭据；把凭据放进纯前端，等于把配额交给任何访客。

### 决策
1. **主路径全部零凭据**：Earth Search STAC（检索）+ AWS 公开 COG（数据）+ 公共 titiler（渲染）+ EOX 年度镶嵌（底图）。
2. **账号型服务（CDSE Sentinel Hub）只做可选增强**，默认隐藏，且移除后站点功能完整。
3. 每一层都有**同级替代**：检索可换 CDSE STAC v1；渲染可换客户端 `geotiff.js`；底图可换 OSM。
4. 降级链 D0–D4 写死在 `services/render/fallback.ts`，任何失败都必须落到"至少还有缩略图和链接"。

### 后果
- ✅ 部署即用，零注册、零密钥泄露面、零配额风险。
- ✅ 站点可长期存活（无账单）。
- ❌ 拿不到像元级云掩膜与指数计算（首版接受，P6 再补）。
- ❌ 依赖两个"公共演示"性质的服务（titiler、EOX），需要 ADR-002 的工程化对冲。

### 被否决的方案
| 方案 | 否决理由 |
|---|---|
| 以 CDSE Sentinel Hub WMS 为主 | 需账号；凭据必暴露；配额可被滥用至封号 |
| Sentinel Hub "公共演示 instance" | 无授权、无 SLA、随时失效，且可能违反服务条款 |
| 自建后端代理（own tile server） | 违反"纯前端优先、无自建后端"约束 |
| 只用 EOX 年度镶嵌 | 不是"最新影像"，无法满足核心诉求 |

## ADR-002: 放弃交互式 XYZ 瓦片，改「视口裁剪单图」

**状态**：已接受（2026-11-06）

### 背景
最初设想是标准做法：`L.tileLayer('https://titiler.xyz/cog/tiles/...')`。实测推翻了它：

| 测量 | 结果 |
|---|---|
| 单张 z12 瓦片（已预热） | 0.39 s，26–30 KB ✅ |
| **9 张并发**（约等于一次平移的最小增量） | **总计 10.3 s**（上游排队放大） |
| 一次真实平移/缩放要的瓦片数 | 20–60 张 |

即：单请求看着很美，并发一上来就崩塌。地图交互是**并发密集型**负载，公共演示实例承受不了。

### 决策
1. 主渲染路径改为 **一次交互 = 一个请求**：`/cog/bbox/{bbox}.jpg?...&max_size=1024|2048`（或 `/cog/preview`），一次拿到"当前视口那么大"的一张图，用 `L.imageOverlay` 贴上。
2. 渲染请求**串行化**（并发 1，后到者取代前者），`moveend` 去抖 400 ms，超时 8 s，`AbortController` 取消在途请求。
3. XYZ 瓦片保留为 **T5 可选模式**（z ≥ 15、用户显式开启、队列 ≤ 4），默认关闭。

### 后果
- ✅ 延迟可预测（一个请求 1–5 s），不会因并发爆炸；移动端流量可控（100–500 KB/次）。
- ✅ 与"用户看一块区域、等一张图"的心智模型一致，交互更简单。
- ✅ 请求数恒定，天然对上游友好（不容易被限流）。
- ❌ 平移时不是"无缝瓦片流"，而是"松手后出图"——**图片会跟随视口重取**，做不到 Google Maps 式的连续瓦片。
- ⚠️ 需求若升级为"流畅漫游"，必须切到自建 titiler 或客户端 `geotiff.js`（P6），架构已预留（只改 `renderFlow` 内部，UI 不动）。

### 被否决的方案
| 方案 | 否决理由 |
|---|---|
| 标准 XYZ 瓦片 | 实测并发 10.3 s，不可用 |
| 自建瓦片服务 | 违反约束；且是运维负担 |
| 预生成整景金字塔 | 无后端，无法预生成 |
| 客户端全量解码 COG | 357 MB 单景，浏览器扛不住（窗口化 Range 读取可行，列为 P6） |

## ADR-003: 原生 TypeScript + Leaflet，不引入 React 与 MapLibre

**状态**：已接受（2026-11-06），可撤销

### 背景
需求建议"Vite + 原生/React + Leaflet 或 MapLibre"，"不要过度工程化"。

### 决策
- **UI**：原生 TS + 一个 ~60 行的 `h()` 助手 + 订阅式 store。
- **地图**：Leaflet 1.9（不做 MapLibre）。
- **样式**：原生 CSS + 变量。

判据：本应用有 15 个以内的组件、20 个以内的状态字段、零路由、零表单校验、零列表虚拟化。React 的组件复用与 diff 能力在这里没有对应的问题，却要付出 ~40 KB 运行时与构建链路。

### 后果
- ✅ JS 预算 90 KB 内有富余；首屏更快；依赖更少（安全面更小）。
- ✅ Leaflet 对光栅瓦片不强制 CORS，老 WebView 兼容性好，低端 Android 无 WebGL 依赖。
- ❌ 手写 DOM 更新时若不自觉，会出现"状态与 UI 不同步"。缓解：**单向数据流**——只允许通过 `store.set()` 改状态，组件只订阅渲染，禁止组件内部改自己的展示态。
- ❌ 没有 React 生态（无现成日期选择器/抽屉库）→ 本项目这两种都自写（各约 80 行），反而更小更可控。
- 🔄 **切换路径**：若团队已有 React 规范，把 `ui/*` 换成函数组件、`store` 换 `useSyncExternalStore` 即可，`domain`/`services` 完全不动（这正是分层的目的）。

### 被否决的方案
| 方案 | 否决理由 |
|---|---|
| React 18 | 组件数与状态量撑不起运行时成本 |
| MapLibre GL JS | 需 WebGL；本项目零矢量/倾斜/3D 需求；CSS 化样式系统反而增加复杂度 |
| OpenLayers | 能力过剩（投影/图层体系庞大），包体 200 KB+ |
| Tailwind | 构建与类名噪音；本项目 CSS 总量 < 12 KB |

## ADR-004: 无后端，URL 即状态 + 本地三级缓存

**状态**：已接受（2026-11-06）

### 背景
"纯前端、无账号"意味着没有服务端会话，也没有地方存"用户上次看的地方"。

### 决策
1. **URL hash 是唯一真相**：`#z/x/y?d=..&c=..&p=..&s=..`。所有状态可序列化、可分享、可前进后退。
2. **平移缩放用 `replaceState`**（不污染历史），**选中场景用 `pushState`**（可回退）。
3. **三级缓存**：内存 LRU（渲染结果）→ `localStorage`（查询快照，8 条/10 min）→ IndexedDB（图片，80 MB）。P5 可选 Service Worker。
4. 不使用 Cookie、不接第三方埋点；错误计数只写本地 `localStorage`。

### 后果
- ✅ 分享一个链接就能把"别人看到的画面"复原——这是无账号产品最好的"协作"能力。
- ✅ 刷新、断网重开、二次访问都有即时反馈。
- ❌ URL 会变长（可接受，< 120 字符）；URL 解析必须**极其宽容**（任何畸形都回退默认值，绝不白屏）。
- ❌ 缓存需要显式失效策略（TTL + 版本号 `gm:v1:*`），否则升级后读到旧结构。约定：`Scene` 结构变更必须升缓存命名空间。

### 被否决的方案
| 方案 | 否决理由 |
|---|---|
| IndexedDB 存全部状态 | 首屏异步读取，反而更慢；URL 已够用 |
| 云端保存"我的位置" | 需账号/后端，违反约束 |
| 只用 localStorage 不写 URL | 无法分享（核心价值之一） |

## ADR-005: 云量采用场景级统计 + 明确免责，像元级掩膜延后

**状态**：已接受（2026-11-06）

### 背景
`eo:cloud_cover` 是**整景**（约 110 km × 110 km）平均云量。北京上空一景云量 0.4%，你关心的 1 km² 可能正在云下。这是用户最容易产生"这产品不准"的时刻。

### 决策
1. 服务端只用 `eo:cloud_cover < N` 做粗筛（零成本、零 Key）。
2. 排序用 `thickCloud = s2:high_proba_clouds_percentage + s2:medium_proba_clouds_percentage`，比单一均值更贴近"能否看见地面"。
3. UI 在云量控件下方**常驻**一句说明："整景平均云量，目标区域仍可能被云遮挡"。
4. 空结果时给出可执行的三个动作（放宽云量 / 扩大时间 / 缩小范围），而不是一句"无数据"。
5. 像元级掩膜（SCL / evalscript）列为 P6，并明确它的前置条件（客户端 SCL 计算 或 CDSE 账号）。

### 后果
- ✅ 零成本、零 Key 就解决了 80% 的筛选诉求。
- ✅ 通过 `thickCloud` + 文案 + 兜底引导，把"不准确"转化为"用户可理解"。
- ❌ 仍可能出现"云量 0% 但看不见地面"（薄卷云、局部对流云）。这是数据本身的限制，**必须在产品文案里承认**，而不是靠算法掩盖。
- 🔄 P6 若接入 SCL，`Scene` 增加 `maskAvailable` 字段，渲染层增加叠加开关——**不破坏现有契约**。
